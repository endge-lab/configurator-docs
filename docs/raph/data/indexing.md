# Индексация коллекций

`DefaultDataAdapter` автоматически ускоряет параметризованные сегменты `DataPath` вида `[key=value]`. Например, в пути `orders[id=42].status` индекс относится к массиву `orders`, ключу `id` и значению `42`.

Индекс принадлежит data adapter, а не `DataPath` и не `RaphRouter`. Он используется при обходе параметризованного сегмента в `get`, `has`, `set`, `delete`, `merge` и `indexOf`.

Не смешивайте три независимые оптимизации:

- `DataPath` кэширует разобранное представление путей;
- `RaphRouter` использует дерево маршрутов и caches для сопоставления подписок;
- `DefaultDataAdapter` индексирует элементы массивов для `[key=value]`.

Настройки на этой странице управляют только третьим механизмом.

## Поведение по умолчанию

Обычный `RaphApp` создаёт `DefaultDataAdapter`, у которого индексация включена:

```ts
import { RaphApp } from '@endge/raph'

const app = new RaphApp()

app.set('orders[id=42].status', 'ready')
console.log(app.get('orders[id=42].status')) // ready
```

Runtime defaults:

| Настройка | Значение | Назначение |
| --- | --- | --- |
| `indexEnabled` | `true` | Использовать индекс для `[key=value]` |
| `indexStrategy` | `'eager-all-keys'` | При первой индексируемой операции собрать buckets всех простых полей массива |
| `autoCreate` | `true` | Создать отсутствующий элемент и промежуточные containers при `set` |
| `arrayDelete` | `'unset'` | При удалении оставить разреженную позицию массива |

Название `eager-all-keys` относится к охвату полей, а не ко времени создания: индекс всё равно строится лениво при первом параметризованном обращении к конкретному массиву.

## Как устроен индекс

Для каждого массива adapter хранит отдельную структуру `поле → значение → позиция`. Сам массив является weak key, поэтому индекс не удерживает массив в памяти после того, как тот становится недоступен приложению.

Индексируются только простые значения полей plain-object элементов:

- `string`;
- `number`;
- `boolean`.

`null`, `undefined`, вложенные объекты и массивы не добавляются в buckets. Сравнение значений остаётся строгим: числовой `42` и строковый `'42'` — разные selector values.

Первое обращение строит индекс за линейный проход по массиву. После прогрева найденное значение извлекается из `Map` за среднее константное время; обход остальных сегментов пути и работа runtime при этом никуда не исчезают. Если значения нет в bucket, adapter выполняет линейный fallback. Отрицательный результат не кэшируется, поэтому повторяющийся поиск отсутствующего значения остаётся линейным.

## Стратегии

### `eager-all-keys`

При первом selector lookup adapter один раз проходит массив и индексирует все простые поля его plain-object элементов. Стратегия полезна, когда одна коллекция регулярно выбирается по нескольким ключам, например `id`, `code` и `slug`.

Цена — больше работы при первом обращении и больше памяти на buckets, включая поля, которые могут больше не использоваться для поиска.

### `lazy-key`

При первом обращении строится bucket только для запрошенного ключа. Новый selector key вызывает ещё один линейный проход по массиву.

Стратегия полезна для широких объектов, когда поиск стабильно выполняется по одному-двум полям.

## Настройка adapter

```ts
import { DefaultDataAdapter, RaphApp } from '@endge/raph'

const adapter = new DefaultDataAdapter(
  {
    orders: [
      { id: 1, status: 'draft' },
      { id: 2, status: 'ready' },
    ],
  },
  {
    autoCreate: true,
    arrayDelete: 'splice',
    indexEnabled: true,
    indexStrategy: 'lazy-key',
  },
)

const app = new RaphApp()
app.options({ adapter })

console.log(app.get('orders[id=2].status')) // ready
```

В текущем TypeScript-контракте при передаче options указывайте `indexStrategy` явно. Runtime имеет default, но явная стратегия делает стоимость первого доступа предсказуемой.

Настройки можно изменить после создания:

```ts
adapter.options({
  indexEnabled: false,
  indexStrategy: 'lazy-key',
})
```

Отключение индекса возвращает линейный поиск на каждую операцию. Смена стратегии сбрасывает построенные indexes; они будут созданы заново по требованию.

## Жизненный цикл и invalidation

Adapter поддерживает индекс при операциях, где ему известен затронутый массив:

- первое обращение создаёт buckets;
- создание элемента через параметризованный `set` дополняет существующий индекс;
- замена элемента по числовой позиции помечает индекс массива для перестроения;
- удаление через `splice` инвалидирует индекс, потому что позиции сдвинулись;
- параметризованный `unset` удаляет точное selector value из bucket;
- `replaceRoot` и смена стратегии очищают все indexes.

Следующее selector-обращение после invalidation перестраивает индекс автоматически.

## Требования к данным и ограничения

Используйте для selector стабильный уникальный ключ, например immutable `id`.

::: warning Уникальность selector
При повторяющихся значениях индекс хранит последнюю встреченную позицию, а линейный поиск без индекса возвращает первую. Дубликаты делают результат зависимым от режима и не должны использоваться как selector contract.
:::

Все структурные изменения индексируемых массивов проводите через adapter. Прямое изменение объекта, полученного из `adapter.root()`, обходит invalidation. В прогретом индексе также не меняйте selector key через вложенный `set` или `merge`: для смены идентификатора замените элемент по числовой позиции либо замените root/коллекцию так, чтобы adapter сбросил индекс.

При `arrayDelete: 'unset'` предпочитайте параметризованное удаление `orders[id=42]`. Числовое удаление `orders[3]` оставляет hole и не сообщает индексу, какие selector values исчезли. Если допустимо сдвигать позиции, `arrayDelete: 'splice'` обеспечивает полную инвалидацию массива.

Пользовательский `DataAdapter` не получает этот механизм автоматически: реализация сама определяет способ и гарантии поиска `[key=value]`.

## Как выбирать режим

| Сценарий | Рекомендация |
| --- | --- |
| Частые lookup по нескольким полям большой коллекции | `eager-all-keys` |
| Частые lookup по одному стабильному полю | `lazy-key` |
| Маленький массив или редкие единичные lookup | Измерить; линейный режим может быть дешевле первого build |
| Много запросов отсутствующих значений | Учитывать линейный fallback на каждый miss |
| Selector keys изменяются in-place | Сначала изменить модель mutations или явно заменять коллекцию |

Не оценивайте ускорение по первой операции: она включает построение индекса. Сравнивайте отдельно cold lookup, warmed lookup, стоимость mutations и расход памяти на реальном размере коллекции.
