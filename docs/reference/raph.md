# Raph в Endge

Raph (`@raphy-js/raph`) — библиотека реактивных данных, на которой работает runtime `@endge/core`. В Raph лежат данные смонтированных Store и Composition. Raph пересчитывает производные поля и сообщает потребителям об изменениях.

Автор конфигураций не вызывает Raph напрямую. Он пишет пути данных и рецепты изменений в Source, а Core передаёт их Raph. Эта страница описывает то, что из Raph нужно знать автору конфигураций и интегратору Endge. Endge и Raphy — независимые экосистемы; полное руководство Raph ведётся на сайте Raphy (см. [ниже](#полная-документация-raph)).

## Пути данных

Путь данных (DataPath) — строка, которая адресует значение внутри данных: поле объекта, элемент массива по номеру или по значению поля.

| Запись | Сегмент | Что адресует |
| --- | --- | --- |
| `rows`, `profile.name` | ключ | поле объекта; сегменты разделяются точкой |
| `rows[0]` | индекс | элемент массива по номеру с нуля |
| `rows[id="r-1"]`, `rows[id='r-1']` | селектор | первый элемент-объект, у которого собственное поле `id` строго равно значению |
| `rows[id=3]`, `[active=true]`, `[parent=null]` | селектор | значение без кавычек — число, `true`, `false` или `null`; `[id=3]` не находит `"3"` |
| `rows[id=$id]`, `rows[$i]`, `rows[0].$field` | переменная | `$имя` подставляется из переменных пути |

Правила грамматики:

- сегменты комбинируются в любом порядке: `groups[id="g-1"].rows[0].title`;
- переменная в индексе `[$i]` должна быть целым числом от нуля, в значении селектора — числом, строкой, `true`, `false` или `null`, в позиции ключа — строкой или числом без `.`, `[` и `]`;
- слово без кавычек в селекторе, например `[status=open]`, читается как строка `"open"`; кавычки делают такую запись однозначной;
- ключ, содержащий `.` или `[`, адресовать нельзя: экранирования ключей нет;
- `*` и `[*]` в Raph означают маску подписки; в путях чтения и записи Endge они запрещены.

### Где какой синтаксис

Полная грамматика работает не везде. В некоторых местах Source путь остаётся точечным: селекторы, индексы `[n]` и `$имя` там не разбираются.

| Место | Синтаксис | Источник переменных |
| --- | --- | --- |
| Чтение в [функциональных выражениях](/reference/value-expressions#синтаксис-путеи): readers, `get`, `getOr`, `has`, `pick`, `match`, ключи `join`/`lookup`, outputs Query, `path()` и шаблоны DataView | полный | props выражения или DataView |
| [Update](/reference/update#mutations): `target`, `ifExists`, `meta(path, namespace)`, readers `data`, `hasData`, `meta`, `hasMeta` | полный | `vars` mutation |
| Update: `valueFrom`, значения `vars`, `forEach`, readers `input`, `item`, `parent` | точечный путь в payload | — |
| Composition: `fromData('alias.поле')` | точечный путь; части читаются буквально | — |
| Пути записи `set`, `unset`, `rename`, `enrich` в выражениях, readers обновлений Store, маршрутизация Stream | точечный путь | — |

### Чтение и запись ведут себя по-разному

| Ситуация | Чтение в выражении | Запись в Update |
| --- | --- | --- |
| Селектор не нашёл элемент | результат `undefined`, `has` — `false` | `set` и `merge` **добавляют** в конец массива новый элемент с этим полем, например `{ id: "r-9", ...patch }` |
| `$имя` не задана, позиция ключа | ключ читается буквально: так работают поля вида `$type` | diagnostic `update-var-required`: каждая `$имя` в `target`, `ifExists` и readers `data`/`meta` объявляется в `vars` |
| `$имя` не задана, внутри `[...]` | `undefined` и предупреждение `value-path-variable` | то же требование `vars` |
| Значение переменной `null` или пустая строка | — | Update завершается ошибкой «cannot resolve var» |
| Синтаксическая ошибка в пути | литеральный путь — diagnostic `source-expression-path-invalid` при компиляции | компиляция проверяет только `.`/`..` в начале и wildcard (`update-target-wildcard`); остальное — ошибка при обработке события, до записи |

Чтобы Update только обновлял существующие элементы, добавьте `ifExists` с тем же путём. Без `ifExists` событие о незнакомом `id` создаст новый элемент.

### Проверенный пример

Store хранит список и производное поле, Update переименовывает элемент по `id` из события. Тела проверены компиляцией workspace (`node scripts/grade-workspace.mjs --markdown docs/reference/raph.md`).

`POST /api/v1/stores`:

```json [POST /api/v1/stores]
{
  "identity": "example-list",
  "displayName": "Пример списка",
  "sourceVersion": 1,
  "source": "defineStore({\n  data: {\n    items: value([]).contract(field('Object').array()),\n    openItems: derived()\n      .from('items')\n      .select(path('').where(match({ status: 'open' })))\n      .contract(field('Object').array()),\n  },\n})"
}
```

`POST /api/v1/updates`:

```json [POST /api/v1/updates]
{
  "identity": "example-list-rename",
  "displayName": "Переименование элемента",
  "storeIdentity": "example-list",
  "sourceVersion": 1,
  "source": "defineUpdate({\n  handles: ['item.renamed'],\n  mutations: [\n    {\n      strategy: 'set',\n      target: 'items[id=$id].$field',\n      ifExists: 'items[id=$id]',\n      valueFrom: 'value',\n      vars: { id: 'id', field: 'field' },\n    },\n  ],\n})"
}
```

Событие `item.renamed` с payload `{ "id": "r-1", "field": "title", "value": "Новое имя" }` запишет `items[id="r-1"].title`. Если элемента `r-1` нет, `ifExists` пропустит mutation. Поле `openItems` пересчитается после записи, его нельзя указать в `target`.

## Реактивность Store

### Что хранится в Raph

Каждый смонтированный Store получает в Raph своё поддерево по runtime-пути экземпляра. Пути в Source отсчитываются от корня этого поддерева: `items` в Update означает поле `items` этого Store. Абсолютный путь Raph автору не нужен.

При монтировании Core записывает начальные значения всех `value(...)`-полей одним батчем. Затем в порядке Source создаются `derived()`-поля и сразу вычисляются.

### Когда пересчитываются производные поля

Производное поле Store зависит от своего `.from('поле')`. Оно пересчитывается при записи в это поле или в любой его вложенный путь, например `items[id="r-1"].title`. Запись в другие поля Store его не трогает.

Пересчёт происходит один раз в конце батча изменений, а не после каждой отдельной записи. Все mutations одного Update применяются одним батчем: производные поля увидят итоговое состояние, а не промежуточное. Производное поле Store пересчитывается целиком. Инкрементальные стратегии (`collectionByKey`) выбирает DataView в Composition, см. [DataView](/reference/data-view#incremental-materialization).

### Порядок Update

1. Для каждой mutation вычисляются `vars`, `when` и значение. Все выражения читают состояние **до** изменений.
2. План целиком проверяется на копии данных. При ошибке ничего не записывается.
3. План применяется одним батчем, затем пересчитываются производные поля и уведомляются потребители.

Если mutation должна увидеть результат предыдущей, разделите их на два Update и вызовите последовательно, подробнее — в [Update](/reference/update#expressions-и-pre-update-state).

### Владение данными

- Store владеет своими данными. В `value(...)`-поля пишут только Update этого Store, публикация Query через `.storeTo(...)` и события Stream через `.dispatchTo(...)`.
- `derived()`-поля доступны только для чтения: запись в них — ошибка компиляции Update.
- Чужой Store читать и изменять из Update нельзя.
- Meta — отдельный слой аннотаций того же пути, например признак оптимистичной записи. `meta(path, namespace)` не меняет Data и требует, чтобы путь уже существовал. Аннотировать можно и производное поле.
- Contextual Store, заимствованный другой Composition, не сбрасывается. При уничтожении владельца освобождаются его данные, производные поля и подписки.

Полный контракт — [Store](/reference/store#подключение-и-владение) и [Update](/reference/update#владение-store).

## Что нужно интегратору

Интегратор встраивает Core в приложение или пишет renderer. Для него важны три правила:

- Core сам настраивает Raph и владеет узлами runtime. Конфигурация не создаёт узлы Raph вручную вместо `store(...)` и `component(...)`.
- Данные конфигурации меняются через Update, Action и публичный API Core, а не прямой записью в Raph. Прямая запись обходит проверку владения и таблицу обработчиков Store.
- Раздел Raph нужен при разработке собственного host или renderer, когда эта граница явно определена. Точный API Core — в [встраивании Core](/advanced/core-api).
